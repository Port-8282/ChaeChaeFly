# 서비스 간 API·이벤트 규격

여기서 `contracts`는 **개발 서비스 간 통신 규격**이다. 선박 용선계약 원문을 보관하는 폴더가 아니다.

최종 설계에서는 `api/`에 HTTP API 명세, `schemas/`에 공통 JSON 규격, `examples/`에 최소 JSON 예시를 둔다. `docs/api/`는 사용 설명을 담고 이 원본을 참조한다. 이 파일들은 레포 전체 CI의 규격 검사에 사용하며, 서비스가 실행 중 루트 폴더를 직접 읽도록 구성하지 않는다.

아래는 합의할 필드와 동작의 초안이다. 아직 확정된 API나 구현된 JSON Schema가 아니다. 경로·필수값·오류 응답은 Back·AI·ML·Front 담당자가 합의 후 파일로 작성한다.

## 이벤트 입력

- `event_id`: 중복 전송을 식별하는 ID.
- `event_type`, `entity_id`: 어떤 선박·부두의 무슨 변화인지.
- `source_version`: 같은 대상 이벤트의 순서를 판단할 값. 여러 송신자가 있으면 우선순위·충돌 규칙을 추가한다.
- `occurred_at`: 발생 시각. 시간대가 있는 ISO 8601 형식을 사용한다. 이 값 하나만으로 중복·순서를 판정하지 않는다.
- `payload`: 변화한 데이터. 고정 정보와 실시간 상태 필드의 소유자를 정한다.

Back이 검증·반영한 뒤 `state_version`을 부여한다. 중복 이벤트는 상태를 다시 바꾸지 않는다.

## 계산 요청·결과

- `calculation_id`: 계산 한 건의 ID.
- `state_version`: 어떤 상태를 기준으로 계산하는지.
- 입력 스냅샷: 선박·부두·예상 일정·계약 규칙·예보 등 계산 기준 전체.
- `model_version`, `rules_version`: 사용한 모델과 계산 규칙의 버전.
- 결과: 후보 ID, 접안 일정, 예상 체선료·조출료·대기시간, 제약 검증 결과, 계산 근거.
- 상태: `queued`, `running`, `succeeded`, `failed`, `superseded`를 구분하는 안. API 담당자가 전이 규칙을 정한다.

기존 체선료 계산기 필드 이름은 통합 시 실제 스키마와 대조한다. `effective_start_local`은 계산 개시 시점이며 NOR 통지 시점과 같은 필드로 취급하지 않는다. 과거 SOF를 예상 계산의 필수 입력으로 넣지 않는다.

## ML 추론

입력 특징·단위·결측값 처리, 요청 모델 버전, 예측 하역시간과 단위, 응답 모델·전처리 버전, 준비 상태와 오류 코드를 정한다. 고정 모델을 찾지 못했을 때 다른 버전으로 조용히 대체하지 않는다.

## 후보 선택·보고서

선택 요청은 `calculation_id`, `candidate_id`, `reason`을 포함한다. Back은 후보가 현재 유효한지 확인하고 선택 당시 스냅샷을 저장한다. 보고서는 이 스냅샷으로 작성하며 최신 DB 값을 섞지 않는다.

모든 경계를 통과하는 로그에는 `request_id`, `calculation_id`, `state_version`, `model_version` 등 해당 작업의 추적값을 연결한다.
