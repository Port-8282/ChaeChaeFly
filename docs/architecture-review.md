# 서비스 구조·Jenkins CI/CD 재검토

> 2026-11-04 · 설계 및 현재 파일에 대한 검토. 실제 서비스 실행·Jenkins 배포·복구 성공 검증은 아직 아니다.

**6개 앱 서비스 구조는 현재 MVP 방향에 맞는다. 연결 구조를 늘리기보다 작업 상태·버전·배포·복구 규칙을 보완해야 한다.**

## 유지하는 구조

단일 레포, Docker Compose, Jenkins를 사용한다. 앱 서버에는 `proxy`, `front`, `back`, `ai`, `ml`, `db`를 배치하는 안이다. Jenkins Controller·Agent는 별도 관리 역할이며 실제 설치 위치는 미정이다.

Back이 DB를 관리하고 AI에 계산을 요청한다. AI는 ML에 하역시간을 요청하고 규칙 Tool로 비용을 계산한다. LLM 설명·보고서는 숫자 결과 표시와 분리한다. ML 학습은 별도 작업이다.

## 보완한 실행 규칙

**1. 긴 계산 때문에 조회가 막히지 않게 한다.**

Back이 계산 요청을 DB에 기록하고 계산 ID를 반환한다. 제한된 작업 실행 코드가 AI를 호출한다. 초기에는 Back 내부 작업 실행과 DB 기록을 사용하며, 별도 메시지 큐 서비스는 추가하지 않는다. 작업 점유·만료·재시작 시 재시도·최대 횟수가 필요하다. 프로세스 메모리에만 작업을 보관하면 재시작 때 잃을 수 있다.

**2. 새 상태와 오래된 계산을 구분한다.**

`event_id`로 중복을 걸러내고 대상별 이벤트 순서를 검증한다. 입력을 반영할 때 상태 버전을 부여한다. 계산은 해당 상태의 스냅샷을 사용한다. 늦게 끝난 계산의 버전이 현재 상태와 다르면 이력으로 보관하고 최신 추천을 덮어쓰지 않는다. 화면에는 이전 결과와 재계산 중 표시를 구분한다.

**3. ML 준비·버전과 재시도 범위를 정한다.**

프로세스가 켜졌다는 것과 모델 로드가 끝났다는 것은 다르다. ML은 모델·전처리를 로드하고 추론 가능할 때 준비 완료로 응답한다. 한 계산은 같은 모델 버전을 사용한다. 요청 버전 불일치 시 해당 결과를 섞지 않고 새 버전으로 전체 계산을 다시 시작하되 횟수를 제한한다. Back의 저장 결과 조회는 ML 준비 상태에 묶지 않는다.

Compose는 기본적으로 준비 완료까지 기다리지 않으므로 시작 의존성에 healthcheck와 `service_healthy` 조건을 설계한다. 실행 중 장애의 타임아웃·재시도·재연결은 앱에서 별도로 처리한다. [Docker 시작 순서 문서](https://docs.docker.com/compose/how-tos/startup-order/)

**4. 선택한 보고서의 기준을 보존한다.**

선택 요청의 계산 ID·후보 ID가 유효한지 확인한다. 낡은 추천이면 재계산 결과를 기준으로 재선택하도록 안내하는 것을 기본안으로 한다. 선택 시 일정·비용·입력 상태·모델 버전·사유를 함께 저장하고 보고서는 이 스냅샷을 사용한다.

**5. 통신 경계와 추적값을 정한다.**

외부 앱 접속은 프록시로 통합하고 AI·ML·DB는 내부 통신으로 둔다. 요청에는 타임아웃과 오류 응답이 필요하다. 로그에 요청·계산 ID, 상태·모델 버전, 처리시간과 오류를 남긴다. 프록시의 실시간 연결 설정, TLS·인증·접근 범위는 환경 확정 후 결정한다.

## 보완한 Jenkins 흐름

협업 브랜치는 feature → dev → main으로 관리한다. main·dev는 PR·1명 승인으로 보호하고 main은 같은 저장소의 dev PR만 허용한다. 아래는 코드·모델의 배포 단계이며, dev 통합 검증과 실제 운영 배포는 구분한다. [GitHub 규칙 적용 안내](infra/github-rules.md)

```text
PR → 검사·테스트 → 결과 기록

신뢰한 코드 변경 / 검증된 모델 출시 요청
                  ↓
Controller가 Agent에 배정
                  ↓
검사 → 이미지 빌드 → 단위·호환 테스트
                  ↓
Registry에 검증 이미지 저장
                  ↓
전체 릴리스 버전 명세 작성
                  ↓
앱 서버 공통 배포 잠금
                  ↓
DB 변경이 있으면 백업·호환 확인·migration
                  ↓
지정 이미지 pull → 대상 서비스 갱신
                  ↓
준비 상태 + 전용 시연 데이터 통합 확인
                  ↓
성공 릴리스 기록 / 실패하면 이전 앱 복구·재확인
```

**빌드 환경·권한:** Controller에서 앱 빌드를 하지 않고 Agent에 Git·빌드 도구·Docker/BuildKit 환경을 준비한다. PR 작업에는 운영 SSH 키와 Registry 쓰기 권한을 주지 않는다. 신뢰한 출시 작업의 실행 환경·Credentials 범위를 분리한다. Controller·Agent가 꼭 물리적으로 다른 서버여야 한다는 뜻은 아니다. [Jenkins Controller 격리](https://www.jenkins.io/doc/book/security/controller-isolation/), [빌드 보안](https://www.jenkins.io/doc/book/security/securing-builds/)

**전체 버전 기록:** Front·Back·AI·ML뿐 아니라 proxy·DB 이미지 digest도 고정한다. Git commit, 모델 버전·artifact 위치·SHA256, API·전처리 규격, Compose·프록시 설정 버전, DB migration 버전을 기록한다. 변경하지 않은 서비스도 기록하며 Registry에 직전 성공 이미지를 보관한다.

**ML만 바뀐 경우:** 검증된 artifact를 명시적으로 지정하고 ML 이미지와 기존 AI의 호환을 확인한다. 호환되면 ML만 갱신한다. 다른 서비스 버전은 유지한다. 공통 API·전처리 의미가 바뀌면 관련 서비스까지 검사한다. 실행 중 모델 파일 덮어쓰기는 사용하지 않는다.

**배포 충돌·실패:** 코드 배포와 모델 출시가 같은 서버 잠금을 공유한다. 배포 실패 시 직전 성공 릴리스의 앱 버전을 복구하고 다시 확인한다. 단일 ML 인스턴스 교체에는 일시 중단이 가능하며 무중단 추론을 보장하지 않는다.

**DB 변경:** migration은 버전 관리하고 배포 작업에서 1회 실행하도록 한다. 이전 앱과 새 DB 구조가 호환되어야 앱만 되돌릴 수 있다. 호환되지 않는 변경의 복구 계획이 없으면 배포를 중단한다. DB 전체 복원은 신규 데이터 손실 가능성이 있어 일반 앱 복구와 분리한다.

## 저장 공간·백업

DB 영속 볼륨은 유지한다. 앱 서버 디스크 장애와 함께 사라지지 않는 위치에 DB 백업을 보관하고 별도 DB로 복원해 본다. Jenkins 상태·설정도 영속 저장과 별도 백업이 필요하다. 모델 artifact와 릴리스 기록 역시 복구에 사용할 수 있도록 보관한다. [Docker 볼륨 문서](https://docs.docker.com/engine/storage/volumes/)
