# Github Rules

PORT 8282 · ChaeChaeFly 팀 공통 협업 규칙

# Dev, Prod 전략

- **main (Prod)**
  - **운영에 반영할 검증된 코드를 관리하는 브랜치**
  - **같은 저장소의 `dev`에서 올라온 PR만 병합**
  - 작성자를 제외한 **4명 이상의 Approve 필요**
  - **PR의 리뷰 대화 전부 Resolve 필요**
  - **PR만 허용하며 직접 push·force push·브랜치 삭제 금지**

  > **코멘트:** Approve는 리뷰어의 승인, Resolve는 개별 리뷰 대화를 처리했다는 표시입니다. 서로 다른 절차이므로 `main`에 병합할 때는 둘 다 확인합니다.

- **dev**
  - **각 feature의 변경을 모아 통합 검증하는 브랜치**
  - 작성자를 제외한 **1명 이상의 Approve 필요**
  - **PR만 허용하며 직접 push·force push·브랜치 삭제 금지**
  - 리뷰 지적사항을 처리한 뒤 병합. 대화 해결을 강제하는 설정은 권장
  - 통합 검증을 마치면 `dev → main` PR 제출
  - `main → dev` 이력 동기화 PR도 같은 승인 규칙 적용

  > **코멘트:** `dev`에서는 각자 만든 기능을 연결해 봅니다. 예를 들어 Back의 API 변경이 Front 화면과 AI 호출에도 맞는지 함께 확인합니다.

- **feature**
  - **각자 기능을 개발하는 작업 브랜치**
  - 최신 `dev`에서 생성하고 한 브랜치에서 하나의 목적에 집중
  - 브랜치명: **`feature/영역-업무내용`**
  - 영문 소문자·숫자·하이픈 사용. 브랜치명에 이슈 번호는 필수 아님
  - 예: `feature/front-dashboard`, `feature/ai-demurrage`, `feature/infra-compose`
  - 기능·테스트·문서를 확인한 뒤 **`dev`로 PR 제출**
  - **`dev`에 병합한 후 삭제**. `main`과 `dev`는 유지

  > **코멘트:** 브랜치 하나에 서로 다른 작업을 섞으면 리뷰 범위가 커집니다. `feature/infra-compose`에서는 Compose 구성처럼 한 작업에 집중합니다.

초기 공통 커밋과 `main`·`dev` 준비를 마친 뒤 `feature → dev → main` 순서로 작업합니다. 다른 사람의 변경이나 공유 브랜치 이력을 임의로 삭제·재작성하지 않습니다.

# PR, Issue

> **코멘트:** Issue는 문제나 요청을 남기는 기록이고, PR은 변경 내용을 검토받고 브랜치에 합치기 위한 요청입니다. 둘을 연결하면 왜 수정했는지 따라가기 쉽습니다.

1. **버그, 요청사항은 재현하거나 작업할 수 있을 만큼 상세히 작성합니다.**

   - 버그 발견 시 **GitHub Issue에 먼저 재현 방법·기대 결과·실제 결과를 작성**하고, 링크를 Slack·ZEP 등 팀 채널에 공유합니다.
   - PR에는 관련 Issue를 연결합니다. 연결할 이슈가 없으면 `없음`으로 적습니다.
   - **괄호 안 도움말·예시값·안내 주석은 반드시 지우거나 실제 내용으로 바꿉니다.**
   - 작업 내용, 변경 사항, 스크린샷·API 테스트 결과, 참고 사항과 리뷰 요청을 작성합니다.
   - API·환경변수·DB·모델 변경이 다른 파트에 미치는 영향을 적습니다. API 호환을 깨는 변경은 제목·본문에 명시하고 전환 방법을 설명합니다.
   - 계산 변경은 입력·규칙·정답 비교 결과를, 모델 변경은 평가 결과·모델 버전을 남깁니다.
   - 미해당 항목은 `해당 없음`, 실행하지 않은 검사는 `미실행: 이유`로 적습니다. 작업 중인 PR은 Draft로 올립니다.
   - 비밀값·실제 업무자료·모델 바이너리·DB 데이터와 백업은 포함하지 않습니다.

## PR 타이틀 규칙

**`[영역] 작업 내용`**

- **영역:** `front`, `back`, `ai`, `ml`, `training`, `infra`, `api`, `data`, `docs`, `repo` 중 하나를 적습니다. 여러 서비스의 변경을 묶는 배포 준비·동기화 PR은 `repo`를 사용합니다.
- **작업 내용:** PR 전체에서 무엇을 바꿨는지 한 줄로 요약합니다. `추가`, `수정`, `정리`처럼 변경을 나타내는 말과 구체적인 대상을 함께 적습니다.
- 영역은 영문 소문자로 적고, 대괄호 뒤는 한 칸 띄웁니다. PR 제목에는 타입·이모지·외부 티켓 키를 넣지 않습니다.
- API 호환을 깨는 변경은 제목에 `호환성 변경`을 표시하고, 본문에 소비 서비스의 수정·전환 방법을 적습니다.

| PR 상황 | 제목 예시 |
| --- | --- |
| 기능 추가 · `feature → dev` | `[front] 대기 선박 필터 추가` |
| 초기 설정 · `feature → dev` | `[infra] Docker Compose 설정 추가` |
| 버그 수정 · `feature → dev` | `[ai] 기상 제외 시간 중복 차감 수정` |
| 문서 작업 · `feature → dev` | `[docs] GitHub 협업 규칙 정리` |
| 배포 준비 · `dev → main` | `[repo] 대시보드·접안 추천 기능 배포 준비` |
| 이력 동기화 · `main → dev` | `[repo] main 병합 이력 dev 동기화` |

> **코멘트:** `수정`, `작업 완료`, `최종`만 적으면 리뷰어가 변경 내용을 알기 어렵습니다. `[ai] 체선료 중복 계산 수정`처럼 무엇을 고쳤는지 제목에 남깁니다.

승인 기준은 작성자 외 `main` 4명 이상, `dev` 1명 이상입니다.

PR 제목은 작성자가 직접 입력합니다. 템플릿은 본문 양식을 제공하며 제목을 자동으로 채우거나 검사하지 않습니다.

## Commit 단위

- **기능·수정 목적별로 작게 커밋합니다.**
- 관련 코드·테스트·문서는 함께 이해하고 되돌릴 수 있는 단위로 묶습니다. 파일마다 따로 커밋할 필요는 없습니다.
- 하나의 변경에 여러 타입이 해당하면 주된 목적을 기준으로 선택합니다.

> **코멘트:** 대시보드 필터 추가와 배포 설정 변경처럼 목적이 다른 작업은 커밋을 나눕니다. 그래야 한쪽만 검토하거나 되돌리기 쉽습니다.

### 깃헙 커밋 규칙

커밋 메시지는 **`type: [영역] 작업 내용`**으로 작성합니다. 외부 티켓 키는 넣지 않습니다.

| 작업 타입 | 작업 내용 |
| --- | --- |
| update | 기존 파일에 새로운 기능 추가 |
| add | 새 파일 생성·초기 설정 |
| bugfix | 재현되는 버그 수정 |
| refactor | 외부 동작을 유지하면서 코드 구조 개선 |
| fix | 버그 수정·구조 개선 외의 작은 코드·설정 수정 |
| move | 파일·폴더 이동 또는 이름 변경 |
| del | 기능·파일 삭제 |
| test | 테스트 코드 작성·수정 |
| style | CSS·화면 스타일 수정 |
| gitfix | `.gitignore` 수정 |
| script | `package.json`·`pyproject.toml`·lock 파일·빌드 및 배포 스크립트 변경 |
| docs | 문서 작성·수정 |
| etc | 기존 타입에 해당하지 않는 기타 작업 |

영역은 `front`, `back`, `ai`, `ml`, `training`, `infra`, `api`, `data`, `docs`, `repo` 중에서 선택합니다.

```text
add: [infra] Docker Compose 설정 추가
update: [front] 대기 선박 필터 추가
bugfix: [ai] 기상 제외 시간 중복 차감 수정
docs: [docs] GitHub 협업 규칙 정리
```

> **코멘트:** 커밋 메시지 `update: [front] 대기 선박 필터 추가`에서 `update`는 작업 타입, `[front]`는 담당 영역, 뒤 문장은 바뀐 내용입니다. PR 제목은 `[front] 대기 선박 필터 추가`로 씁니다.

문서만 작성·수정하는 작업은 `docs`를 사용합니다. 기존 타입으로 분류하기 어려운 기타 작업은 `etc`를 사용하고 제목에 구체적인 작업 내용을 적습니다. GitHub가 자동으로 만드는 Merge commit 제목은 기본 형식을 사용해도 됩니다.

Squash merge 시 최종 커밋 제목은 `type: [영역] 작업 내용`으로 맞춥니다. PR 제목은 `[영역] 작업 내용`을 유지합니다.
