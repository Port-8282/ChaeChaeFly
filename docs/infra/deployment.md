# 배포·검증·복구 계획

> 공통·개발용 Compose는 구현했다. 이 문서는 향후 서버 배포 절차이며 운영용 Compose·배포 실행 스크립트는 아직 구현 전이다. Jenkinsfile은 검사·빌드용 CI만 구현했으며 [CI 안내](ci.md)를 따른다.

## 코드 변경

feature → dev PR에서 관련 검사를 수행하고 dev에서 통합 검증한다. dev → main PR을 승인한 뒤 운영 릴리스 절차를 실행한다. main 병합과 실제 배포 성공은 구분하며 자동 배포·별도 승인 여부는 아직 미정이다.

Jenkins Agent가 검사·이미지 빌드·호환 테스트를 수행한다. 검증 이미지를 Registry에 저장하고 앱 서버가 고정 버전을 받아 실행한다. Controller에서 앱 빌드를 실행하지 않는다.

## 배포 절차

1. 6개 서비스의 이미지 digest, Git commit, 모델·전처리·API·규칙 버전과 모델 해시, Compose·프록시·DB migration 버전을 기록한다.
2. 코드 배포와 모델 출시가 공유하는 서버 배포 잠금을 잡는다.
3. DB 변경이 있으면 백업·이전 앱과의 호환·migration 실행 계획을 확인한다.
4. 지정 이미지로 대상 서비스만 갱신한다.
5. API·DB 연결·ML 모델 로드·버전을 확인한다.
6. 전용 가상 데이터로 계산·조회·화면 반영을 확인한다.
7. 성공 릴리스 또는 실패·복구 결과를 기록한다.

## 모델 출시

검증 모델의 위치·SHA256·평가 결과를 지정한다. 승인된 main의 추론 코드와 함께 ML 이미지를 빌드하고 기존 AI와 호환을 확인한다. 모델 교체 중 예측에 일시 중단이 생길 수 있다. 제한된 대기·재시도와 계산 내 모델 버전 고정을 구현한다.

## 복구·백업

앱 배포 실패 시 직전 성공 릴리스의 이미지·설정 조합으로 복구하고 다시 확인한다. DB 구조가 이전 앱과 호환되지 않으면 앱만 되돌려 복구 완료로 처리하지 않는다.

DB 데이터 복원은 신규 데이터 손실 범위를 확인하는 별도 절차다. 백업은 서버 디스크 장애와 함께 잃지 않는 위치에 보관하고 별도 DB에서 복원 검증한다. Jenkins 상태와 모델 artifact·릴리스 기록도 복구할 수 있도록 보관한다.
